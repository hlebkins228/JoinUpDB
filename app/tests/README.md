# Лабораторная работа № 2

Запуск из `app`:

```sh
make test-ci
```

Нужны работающий Docker Engine / Docker Desktop с интеграцией WSL и Docker
Compose. Docker скачивает зависимости, собирает отдельный контейнер запуска
тестов, запускает PostgreSQL и backend. Локальный Go, PostgreSQL, npm и Java
для этой команды не нужны.

Этапы выполняются последовательно: 10 unit-сценариев ЛР1 → 3 интеграционных
теста отзывов → 1 HTTP e2e. При ошибке оставшиеся этапы не запускаются и
помечаются в Allure как skipped. Отчёт генерируется и при ошибках.

Интеграционные тесты проверяют создание/чтение отзыва, запрет дубликата и
запрет отзыва на будущее событие. Используются настоящие сервисы,
PostgreSQL-репозитории и UOW. Моки остаются только в unit-тестах ЛР1.
Каждый интеграционный сценарий находится в отдельном `*_integration_test.go`.
E2E расположен в `internal/e2e_test/event_e2e_test.go` и вызывает отдельно
запущенный HTTP-сервер: регистрация → вход → создание → чтение → удаление
события → проверка флага удаления. GUI для этого сценария не нужен.

## Изоляция и очистка

Каждый запуск получает отдельный Compose project, сеть и PostgreSQL-инстанс
`joinup_test`; наружу порты не публикуются. Нет общих имён контейнеров и
томов. БД использует tmpfs, схема создаётся существующими Goose-миграциями.
`fixtures.sql` задаёт фиксированные исходные данные, `reset.sql` возвращает
прикладные таблицы к исходному пустому состоянию с сохранением справочника
категорий и миграций. Фикстуры очищаются до и после интеграционных тестов,
между integration и e2e и в EXIT trap контейнера тестов.

Даже при неудачном тесте очищается тестовая БД, а host EXIT trap удаляет
контейнеры, сеть и тома только текущего проекта. При принудительном убийстве
всего хоста отчёт гарантировать невозможно; данные tmpfs исчезнут при
удалении/остановке контейнера. Параллельные локальные запуски используют
разные project name и не затрагивают рабочую БД.

Брокеров сообщений в проекте нет. JWT не хранится как серверная сессия;
сервер на каждом запуске создаёт новый тестовый секрет, а после тестов
удаляются сервер и тестовые пользователи. Токены предыдущего стенда
не подходят следующему запуску.

## Отчёт и трафик

Локальные результаты находятся в `test-report/ci/<уникальный project name>`;
в GitHub Actions — в `test-report/ci`:

- `report.html` — единый статический Allure-отчёт, открывается прямо в браузере;
- `history` — история для следующего запуска и трендов;
- `e2e.pcap` — трафик HTTP-сценария и его повторения через curl;
- `traffic.log` — текстовый вывод tcpdump;
- `curl-replay.log` — результат команд `tests/replay.sh`;
- `stand.log`, `unit.log`, `integration.log`, `e2e.log`, `cleanup.log` — диагностика;
- `allure-results` — исходные результаты, включая skipped при остановке этапов.

`tests/replay.sh` выполняет те же HTTP-действия с отдельным пользователем
`replay_user`. Для просмотра pcap можно использовать Wireshark. Очистка
включает и данные, созданные этим повторением.

В CI история восстанавливается из cache и переносится в новые результаты
до генерации. При локальном запуске история сохраняется в выбранном каталоге
артефактов; для её повторного использования можно задать одинаковый
`TEST_REPORT_DIR` при последовательных запусках.
Обновлённая история получается из обычного Allure-отчёта; второй вызов с
`--single-file` создаёт автономный `report.html` без локального веб-сервера.

## GitHub Actions и Pages

Workflow: `.github/workflows/tests.yml` в корне репозитория. Он запускается
на push, pull request и вручную. Код выкачивается через actions/checkout,
тесты выполняются внутри собранного Docker runner. Для подготовки скачиваемого
отчёта после ошибки сборки контейнера предусмотрена отдельная always-стадия.

В **Actions → нужный запуск → Artifacts → test-report-…** доступен архив с
`report.html`; диагностические файлы находятся в `test-diagnostics-…`.
Allure history сохраняется в GitHub Actions cache отдельно для каждой ветки.

Для публикации нужно один раз выбрать **Settings → Pages → Build and
deployment → Source: GitHub Actions**, затем отправить изменения в GitHub.
Отчёт из основной ветки автоматически публикуется в Pages, включая отчёт
упавшего прогона. Pull request отчёты доступны как artifacts.
Pages URL показывает job `pages`; у стандартного project site он имеет вид
`https://hlebkins228.github.io/JoinUpDB/`, прямой файл — `report.html`.
Существующий сайт Pages в этом репозитории будет заменён страницей отчёта.

Для проверки повторяемости выполнить `make test-ci` дважды, для проверки
параллельности — запустить команду из двух терминалов. Каждому запуску можно
задать собственный путь артефактов через `TEST_REPORT_DIR`.
