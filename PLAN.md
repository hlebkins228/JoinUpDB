## 2. PostgreSQL-триггер для журнала удаления мероприятий

**Цель:** записывать факт мягкого удаления мероприятия в отдельную таблицу средствами PostgreSQL.

Сейчас удаление события реализовано как `UPDATE event SET deleted = true`, поэтому нужен триггер на обновление, а не на SQL-операцию `DELETE`.

### Поведение

- Создать таблицу `event_deletion_log` с полями `id` (идентификатор записи), `event_id` (ID мероприятия), `deleted_at` (время удаления в UTC).
- Создать одну триггерную функцию и один триггер `AFTER UPDATE OF deleted ON event FOR EACH ROW`.
- Выполнять запись только при переходе `OLD.deleted = false` → `NEW.deleted = true`.
- Изменение названия, описания и других полей, а также повторная установка `deleted = true` не должны создавать запись в журнале.
- Запись журнала выполняется в той же транзакции, что и удаление: при откате изменения события запись журнала тоже откатывается.

### Места изменений

- Новая Goose-миграция в `app/migrations/`: создание таблицы, функции и триггера в `Up`; удаление триггера, функции и таблицы в `Down`.
- Существующий `DeleteEvent` в `app/internal/repository/postgres/event.go` уже обновляет флаг `deleted` и будет запускать триггер без отдельной записи журнала из Go.

Задача относится только к PostgreSQL. Для учебной демонстрации журнал просматривается SQL-запросом; отдельный API или интерфейс для него не требуется. Сохраняются только ID события и время удаления.

### Проверка результата

Вручную удалить мероприятие через существующий API и проверить запись в `event_deletion_log`. Проверить отсутствие новых записей при обычном редактировании и повторной установке флага. В отдельной SQL-транзакции установить флаг удаления и выполнить `ROLLBACK`: ни удаление, ни запись журнала не должны сохраниться.

## 3. Наполнение БД: более 1000 записей в каждой прикладной таблице

**Основание:** М, с. 4, п. 1.4; уточнение пользователя — строго более 1000 строк, то есть минимум 1001, в каждой прикладной таблице.

**Сейчас:** в миграциях предусмотрены 11 категорий; общего генератора большого связного набора данных в коде не найдено. Интеграционные тесты создают небольшие наборы для своих сценариев.

**Что сделать:** подготовить воспроизводимый генератор или SQL-сценарий наполнения отдельной учебной PostgreSQL-БД. Соблюдать внешние ключи, уникальность и ограничения значений; после наполнения вывести число строк по таблицам. Даты событий должны подходить для демонстрации будущих и прошедших мероприятий.

**Места изменений:** отдельный сценарий наполнения в `app`, команда запуска в `app/Makefile`. Не помещать массовые демонстрационные данные в обычные миграции схемы.

**Согласованный охват:** все прикладные таблицы итоговой схемы, включая категории, связи и журнал удаления. Журнал заполнять через реальные срабатывания триггера на учебных данных. Не добавлять фиктивные строки в служебные таблицы вроде `goose_db_version`. Наполнение `subscribe` не требует реализации нового API подписок.

**Пресеты:** пользователь подтвердил, что пресеты не используются; функциональность пресетов не реализовывать. Таблица `preset` пока присутствует в миграциях. Уточнить, исключается ли она из итоговой схемы целиком: оставленная прикладная таблица без наполнения противоречила бы требованию к числу строк.

## 4. Роли PostgreSQL: гость, пользователь и администратор

**Основание:** М, с. 4, 11–13.

**Сейчас:** `users.role` и роль в JWT — права приложения. В коде миграций нет создания ролей PostgreSQL и выдачи привилегий; локальное подключение по Makefile использует `postgres`.

**Что сделать:** создать три роли БД — гость, пользователь и администратор — и определить матрицу «роль — объект — разрешённые действия»; добавить сценарий создания ролей и выдачи прав; обеспечить применение соответствующих прав БД для гостевых и авторизованных запросов приложения. Разделить учётные данные миграций/администрирования и обычной работы приложения. Проверить разрешённые и запрещённые действия подключениями с разными учётными именами и сохранить фактические результаты для РПЗ.

**Места изменений:** отдельный SQL-сценарий настройки PostgreSQL, при необходимости `app/internal/settings/settings.go`, `app/cmd/server/main.go`, `app/Makefile` и конфигурация подключений.

**Выбранный вариант:** роли предметной области, а не техническое разделение на читателя, приложение и администратора. Конкретные привилегии и способ выбора роли на соединении определить при проектировании реализации с учётом существующих публичных маршрутов и JWT. Само поле `users.role` не заменяет роли PostgreSQL.
