# Тесты для лабораторной работы № 1

Выбраны бизнес-логика отзывов `ReviewService` и PostgreSQL `ReviewRepo`.
Три test suite содержат по три сценария. Существующие unit-тесты запускаются
отдельно через `make test`.

## Запуск и веб-интерфейс

Из каталога `app`:

```sh
make test-report-serve
```

Команда запускает девять сценариев, измеряет покрытие, генерирует отчёт
Allure и поднимает веб-интерфейс на **http://localhost:9001**. На главной
странице доступны статусы и время тестов, покрытие по файлам, ссылки на
полный Allure-отчёт, HTML исходного кода с покрытием и покрытие по функциям.
В Allure можно просмотреть выполнение фикстур `BeforeAll`, `BeforeEach`,
`AfterEach`, `AfterAll`. Остановка веб-сервера — `Ctrl+C`.

Требуются Go, Python 3, Node.js/npm и Java 8+. При первом запуске Allure CLI
версии 2.46.1 автоматически устанавливается в `.test-tools` внутри проекта;
глобальная установка не нужна. Go-зависимости закреплены в `go.mod` и
`go.sum`. PostgreSQL, MongoDB, Docker, конфиг сервера и Swagger для этих
тестов не требуются.

Другие команды:

```sh
make allure-test                 # тесты, coverage.out, coverage.html и главная страница
make test-report                 # то же и полный HTML-отчёт Allure
make allure-serve                # синоним test-report-serve
make test-report-serve TEST_REPORT_PORT=9002
```

Результаты Allure сохраняются в `allure-results`, веб-отчёт — в `test-report`.
При новом запуске старые результаты сценариев и покрытие заменяются;
статистика относится к текущему запуску. Обе папки и `.test-tools` исключены
из Git. Для самого `make allure-test` Node.js и Java не нужны.

Покрытие измеряется **только девятью сценариями ЛР1** в пакетах
`internal/service` и `internal/repository/postgres`. В общий процент входят
и остальные функции этих пакетов; это не показатель покрытия всего проекта.
HTML позволяет отдельно открыть файлы `review.go` и посмотреть выполненные
и невыполненные участки. Покрытие — доля выполненных операторов, а не ветвей.

Для запуска из IDE включить Go build tag `allure` и выбрать
`TestAllureReviewServiceClassic`, `TestAllureReviewServiceLondon` или
`TestAllureReviewRepo`. Фикстуры работают и без Makefile. Для общего каталога
результатов задать `ALLURE_OUTPUT_PATH` равным абсолютному пути к `app` и
`ALLURE_OUTPUT_FOLDER=allure-results`.

## Жизненный цикл фикстур

| Hook | Действие |
| --- | --- |
| `BeforeAll` | Создаёт контекст с отменой, зависимости и сервисы. В классическом и репозиторном suite создаётся соединение с хранилищем в памяти; в лондонском — mock-объекты. |
| `BeforeEach` | Очищает хранилище и счётчик ID либо сбрасывает вызовы и ожидания mock; задаёт метаданные Allure. |
| `AfterEach` | В лондонском suite проверяет все ожидания mock до записи результата теста в отчёт. |
| `AfterAll` | Закрывает соединение и очищает его данные, отменяет контекст и освобождает ссылки на зависимости. Проверяет закрытие и отмену контекста. |

Создание и освобождение ресурсов выполняются на уровне test suite.
`AfterAll` вызывается и при неудачных assertions в сценариях. Тесты внутри
suite последовательны, не используют `Parallel` и не зависят от порядка:
каждый начинается с пустого хранилища или сброшенных ожиданий.

## Подмена соединения

`internal/testutil/review_connection.go` содержит `ReviewConnection` —
подмену соединения pgx с данными в Go-map. Она поддерживает используемые
`ReviewRepo` операции: создание, проверку уникальности, существования и
чтение списка отзывов. Возвращаются строки с интерфейсами `pgx.Row` и
`pgx.Rows`, поэтому настоящий репозиторий выполняет свои запросы и `Scan`.
Сетевых соединений не создаётся.

`BeginTx` создаёт отдельную копию состояния. `Commit` публикует изменения,
`Rollback` удаляет их. Классические тесты используют **настоящие**
`ReviewService`, PostgreSQL `ReviewRepo` и `UOW`, подменяя соединение.
Получение события остаётся stub с подготовленным событием.

Чтобы передавать такую зависимость, `Pool` и `NewReviewRepo` принимают
существующий интерфейс SQL-операций `sqlRun`, а `NewUOW` — узкий интерфейс
`BeginTx`. Обычный `*pgxpool.Pool` реализует эти интерфейсы и используется
сервером как прежде.

Подмена реализует только операции выбранного сценария; это не SQL-движок
и не проверка синтаксиса запросов, миграций или ограничений настоящего
PostgreSQL. Подмена ответа `Scan` — stub, а соединение с состоянием — fake.

| Набор | Сценарий |
| --- | --- |
| Классический ReviewService | Создание: 2000 Unicode-символов принимаются, пробелы удаляются, оценка 5 и время UTC сохраняются после commit. |
| Классический ReviewService | Повторный отзыв возвращает `ErrAlreadyExists`, исходная запись остаётся единственной и не меняется. |

| Лондонский ReviewService | Репозиторий получает нормализованный текст и оценку 1; передаётся контекст транзакции, выполняется commit, результат преобразуется в DTO. |
| Лондонский ReviewService | Будущее событие: `ErrEventNotPassed`, rollback, без сохранения и commit. |
| Лондонский ReviewService | Ошибка сохранения возвращается вызывающему коду; выполняется rollback, commit отсутствует. |

## Подходы и условия лабораторной

**Классический подход** проверяет результат и состояние, используя настоящий
сервис, репозиторий и UOW над fake-соединением. Он выбран для проверки
сохранения и бизнес-правил без привязки к количеству внутренних вызовов.

**Лондонский подход** через `testify/mock` проверяет взаимодействия, значимые
для транзакций: контекст, нормализованные данные, commit и rollback.
Используются `On(...).Return(...).Once()`, `AssertExpectations`,
`AssertNotCalled` и существующие `mockEventRepo`, `mockUOW`.

**Arrange–Act–Assert:** сначала подготовка данных и ожиданий, затем вызов
проверяемого метода, после этого проверки результата, ошибок и состояния.
Блоки разделены пустыми строками. Первое создание в тесте дубликата относится
к Arrange. Общие зависимости управляются hooks фикстуры.

**Data Builder:** `NewReviewBuilder().WithRating(...).WithText(...).Build()`
задаёт корректные исходные значения и изменяет только существенные для
сценария поля; применяется в сервисных и репозиторных тестах.

**Allure Go** создаёт три явно названных suite с тремя тестами в каждом,
Epic, Feature, теги, assertions и отчёт выполнения фикстур. `Require`
используется для условий, без которых продолжение бессмысленно, `Assert` —
для остальных проверок. Go `-coverprofile` и `go tool cover` формируют
покрытие, Allure CLI — HTML результатов, Python — общую страницу и HTTP-сервер.

Для устойчивости к рефакторингу ошибки сравниваются через `ErrorIs`, SQL
не сравнивается целиком, точное время создания не фиксируется. Событие
датируется относительно текущего времени с запасом в сутки. Граница
2000/2001 проверяется на Unicode-тексте, а не на числе байтов.
