# Памятка по backend JoinUp

Этот файл — карта текущей реализации `app` для будущих задач. Пути ниже указаны относительно `app`, если не оговорено иное. Начинай с этой карты, затем читай файлы затронутого сценария; при расхождениях источником истины служит код. Обновляй памятку при существенных изменениях архитектуры или запуска.

## Правила работы

- Не пиши тесты без явной просьбы пользователя.
- Не добавляй функциональность вне требований. Если для задачи необходима дополнительная функциональность, сначала уточни у пользователя, нужно ли её добавлять.
- При неясных требованиях или нескольких принципиально разных вариантах решения задавай вопросы.
- Опирайся на существующий код, сохраняй его стиль. Не добавляй проверки для очевидно невозможных ситуаций, очевидные комментарии и docstrings без запроса.
- Не исправляй попутно известные особенности, перечисленные ниже: они описывают состояние проекта, а не список поручений.
- Перед изменениями проверяй рабочее дерево; не перезаписывай чужие изменения и не нормализуй окончания строк во всём проекте.
- Триггер удаления, массовое учебное наполнение, роли БД и исследование индексов реализуются только для PostgreSQL. Для MongoDB аналоги не добавлять.
- Все графики должны быть различимы при черно-белой печати: использовать разные типы линий и маркеры, а для столбцов -- штриховку; не различать серии только цветом. Для исследования индекса: без индекса -- сплошная линия с кругами, с индексом -- пунктирная с квадратами. Для изменения оформления вызывать `plot_chart` из `scripts/index_research.py` с сохраненным `summary` из `index_results.json`, без повторных измерений.

## Назначение и стек

JoinUp помогает искать компанию для досуга: регистрация и авторизация, профили, создание и поиск мероприятий, категории, участие, изображения, отзывы и рейтинг организатора.

`app` — самостоятельный Go-модуль `JoinUp`, версия языка в `go.mod` — `1.25.0`. Основные зависимости: Echo **v5**, pgx **v5**, MongoDB driver **v2**, Goose, Zap, validator/v10, jwt/v5, bcrypt, promptui. В обработчиках Echo используется `*echo.Context`.

В корне репозитория находится отдельный React/TypeScript frontend (`../frontend`). Корневой README описывает также планы дальнейшего развития. Не считай их реализованными в backend; Telegram здесь представлен полями со ссылкой на чат и логином.

Поток запроса: маршрут → middleware → handler → service → repository. Интерфейсы определены на стороне потребителей. Сервисы уже зависят от `controller/dto`: не считай их полностью независимым от DTO доменным слоем и не перестраивай архитектуру без задачи. Зависимости передаются вручную через `New...`, обычно конструкторы возвращают значение, а вызывающая сторона передаёт указатель.

В сервисы передаётся `c.Request().Context()`. Для транзакции используется возвращённый `UOW.BeginTx(ctx)` контекст, затем `defer Rollback(ctx)` и явный `Commit(ctx)`. Репозитории извлекают транзакцию через `runFromCtx`: PostgreSQL выбирает pgx.Tx или пул, MongoDB создаёт контекст с сессией. Сейчас транзакциями охвачены создание события, загрузка его изображения с привязкой, создание отзыва и `UpdateEvent`, если передан список категорий.

## HTTP-контракт

Базовый префикс — `/api/v1`. Точный список смотри в `internal/controller/server.go`.

Публичные маршруты:

| Метод и путь | Назначение |
| --- | --- |
| `POST /user` | Регистрация. |
| `GET /auth` | Логин и пароль в заголовках `login` и `password`; ответ `{"token":"..."}` и заголовок `Authorization`. |
| `GET /image/:id` | Байты изображения, Content-Type определяется по содержимому. |
| `GET /event/:id/review` | Список отзывов. |
| `GET /user/category` | Справочник категорий. |
| `GET /user/event/search` | Поиск событий. |
| `GET /user/event/:id` | Чтение события. |

Остальные маршруты группы `/api/v1/user` защищены `Authorization: Bearer <token>`:

| Метод и путь относительно группы | Назначение |
| --- | --- |
| `PUT` без суффикса, `GET /:id` | Изменение своего профиля (`PUT /api/v1/user`) и чтение профиля по ID. |
| `POST /image` | Загрузка изображения, возвращает ID. |
| `POST /event` | Создание события. |
| `PUT /event/:id`, `PUT /event` | Обновление; второй маршрут — существующий вариант с ID в JSON, используемый CLI и интеграционными тестами. |
| `DELETE /event/:id` | Мягкое удаление. |
| `GET /event/created`, `GET /event/joined` | Свои созданные события и события с участием пользователя. |
| `POST /event/:id/join`, `DELETE /event/:id/join` | Присоединение и выход. |
| `PUT /event/:id/image` | Загрузка и привязка обложки. |
| `POST /event/:id/category` | Добавление существующей категории. |
| `POST /event/:id/review` | Создание отзыва. |

JWT подписывается HS256, живёт 2 часа, содержит `UserID` и `Role`. Middleware кладёт `user_id` и `role` в Echo-контекст. Пароли хешируются bcrypt. Регистрация назначает роль `user`; роль `admin` позволяет изменять чужие события. Редактирование, удаление, обложка и категории проверяют права через `EventHandler.checkPerms` → `UserService.CheckPerms`: создатель или администратор. Профиль изменяется по ID из JWT.

Основные соглашения API:

- JSON использует snake_case. Простые сообщения/ошибки — `dto.Msg` (`{"msg":"..."}`); списки обёрнуты в `events`, `categories`, `reviews`.
- Обычно ошибка Bind — 400, Validate — 422, отсутствие — 404, конфликт — 409, неожиданная ошибка — 500 с общим сообщением. Отзывы используют 400 и для валидации. Создание пользователя/события/изображения возвращает 200, отзыва — 201.
- Загрузка файла — multipart с полем `image` или запасным `file`. Изображения хранятся байтами в БД. Загрузка через `/user/image` сама по себе не меняет аватар: его ID задаётся при обновлении профиля.
- Необязательные значения представлены указателями. Координаты в DTO тоже указатели: ноль — допустимое заданное значение. `ToModel` локации вызывается после валидации.
- Время в сервисах и преобразованиях DTO приводится к UTC; JSON-время — RFC3339. Поле API `event_time` соответствует полю БД `event_date`.

## Бизнес-правила

- Событие содержит создателя, название, описание, город, время, локацию, ссылку на Telegram-чат, обложку, категории и участников. Создатель хранится отдельно и автоматически участником не становится.
- Нельзя создать событие в прошлом, редактировать уже прошедшее событие или перенести его в прошлое. Присоединение, добавление категории и изменение обложки также запрещены после времени события. Для выхода и удаления проверки времени нет.
- Удаление устанавливает `deleted = true`. Поиск и списки исключают удалённые события; `GetEvent` по ID возвращает их с флагом. Отзывы удалённого события читать и создавать нельзя.
- Поиск принимает `name`, `event_from`, `event_to`, `city`, `category_id` (запасное имя `category_ids`). Обработчик разбирает повторяющиеся/разделённые запятыми ID, убирает дубликаты и неположительные значения. Требуется наличие **всех** выбранных категорий. Город сравнивается точно, границы времени включительные. Сортировка событий — время, затем ID; без фильтра времени поиск включает прошедшие события.
- При создании категории добавляются к событию отдельными запросами. При редактировании `category_ids` в `UpdateEventRequest` заменяет весь набор категорий; пустой массив снимает все категории, отсутствующее поле сохраняет прежний набор. Категории проверяются по справочнику и сохраняются вместе с событием в транзакции для PostgreSQL и MongoDB. Начальные 11 категорий задаются SQL-миграцией и `internal/repository/mongo/ensure_categories.go`.
- Отзыв: событие уже наступило, автор не организатор, один отзыв на пару событие/автор, рейтинг 1–5, текст после TrimSpace длиной 1–2000 Unicode-символов. **Участие не проверяется**: `IsParticipant` и `ErrNotParticipant` существуют, но `ReviewService.CreateReview` их не использует.
- Список отзывов сортируется от новых к старым (`created_at`, ID). Профиль содержит число созданных/посещаемых событий, число отзывов организатора и среднюю оценку по его неудалённым событиям. Без оценок рейтинг — `null`; сервис округляет его до десятых по half-up.

## Хранилища и схема

Выбор `postgres`/`mongo` задаётся в YAML и применяется в `cmd/server/main.go`. При изменении общего контракта учитывай обе реализации и существующие моки; не делай случайно рабочим только один backend.

PostgreSQL: таблицы `users`, `event`, `location`, `image`, `member`, `category`, `event_category`, `review`, `event_deletion_log`. Локация отдельная, участники и категории связаны таблицами. Создатель, участники и категории догружаются репозиторием, для списков — пакетными запросами. Уникальны логин, пара участник/событие, пара событие/категория и пара событие/автор отзыва. Мягкое удаление события записывается PostgreSQL-триггером в `event_deletion_log`. Для поиска неудалённых событий по городу и дате предусмотрен частичный индекс `event_search_city_date_idx`. Изменения схемы оформляются новой Goose-миграцией. Сервер сам миграции PostgreSQL не запускает.

MongoDB: коллекции `users`, `events`, `images`, `reviews`, `categories`, `counters`. ID целочисленные, выдаются `nextID` через `$inc`, не ObjectID. В событии вложены локация, создатель, участники и категории; в отзыве вложен автор. При старте создаются уникальные индексы логина и пары событие/автор отзыва, выполняется заполнение категорий. Для транзакций нужен replica set; `make run_mongo` настраивает `rs0`.

Отсутствие записи при чтении адаптируется к `sql.ErrNoRows` (включая MongoDB), сервисы преобразуют его в `exceptions.ErrNotFound`. Другие операции могут сразу возвращать ошибки из `exceptions`; ориентируйся на контракт конкретного метода. Ошибки оборачиваются через `%w` и проверяются `errors.Is`.

Различия реализаций, которые нужно учитывать при работе с соответствующим кодом:

- PostgreSQL читает актуальные данные связанных пользователей; вложенные данные MongoDB являются снимками, `UpdateUser` их не обновляет. `ensureCreator` заполняет создателя только при нулевом ID.
- Поиск имени: PostgreSQL использует `ILIKE`, MongoDB — `$regex` без экранирования входной строки; поведение специальных символов различается.
- `ReviewRepo.Create` PostgreSQL не заполняет `Author`, хотя список отзывов заполняет его через JOIN. MongoDB при создании декодирует пользователя с `_id` в `mongoReviewAuthor` с тегом `id`: ID вложенного автора требует отдельного внимания при задаче на отзывы.

## Конфигурация и запуск

Команды Go и Make выполняй из `app`. Для сервера нужен локальный `config.yaml`, исключённый из Git:

```yaml
db: postgres
jwt:
  secret: replace-with-local-secret
logging:
  type: dev
```

Допустимы `db: postgres|mongo`, `logging.type: dev|prod`; все три настройки обязательны. Секрет выше — заглушка. `ReadConfig` сейчас печатает конфигурацию целиком, поэтому не копируй вывод с реальным секретом в отчёты.

- Сервер требует `SERVER_HOST`, `SERVER_PORT`; `make run_server` задаёт `localhost:8080` и переменные подключения.
- PostgreSQL требует `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`. Миграции запускаются локально как `postgres/postgres`, `make seed_db` — как `joinup_admin/admin`, `make run_server` — как `joinup_user/user`. Роли создаются миграцией `20260924002000_roles.sql` при `make migrate_up`; отдельной настройки нет.
- MongoDB использует `MONGO_USER`, `MONGO_PASSWORD`, `MONGO_HOST`, `MONGO_PORT`, `MONGO_DB`. Без host/port/db значения по умолчанию — `localhost`, `27017`, `join_up`; авторизация включается при наличии обоих user/password. Makefile задаёт локальные `mongo/mongo`.
- CLI использует `JOINUP_BACKEND_URL`, по умолчанию `http://localhost:8080`.

Обычный запуск PostgreSQL: создать конфиг → `make swagger` → `make run_db` → дождаться готовности БД → `make migrate_up` → `make run_server`. Для MongoDB: выбрать `db: mongo` → `make swagger` → `make run_mongo` → дождаться готовности replica set → `make run_server`.

| Команда | Назначение |
| --- | --- |
| `go mod download` | Загрузить зависимости из модуля. |
| `make swagger` | Сгенерировать `docs` из Swagger-аннотаций main/handlers/DTO/models. |
| `go build ./...` | Собрать пакеты после генерации Swagger. |
| `make run_server`, `make run_cli` | Запустить сервер или CLI. |
| `make run_db`, `make stop_db` | PostgreSQL 16 в Docker, контейнер `join_up_db`. |
| `make run_mongo`, `make stop_mongo` | MongoDB 7 в Docker, контейнер `join_up_mongo`. |
| `make migrate_up`, `make migrate_down` | Применить миграции PostgreSQL или откатить последнюю. |
| `make migrate_create NAME=change_name` | Создать SQL-миграцию. |
| `make seed_db` | Через `python3` создать 5001 пользователя, по 1–3 события, участия и отзывы. Заменяет учебные данные. Зависимости: `pip install -r scripts/requirements.txt`. |
| `make dicebear_images` | Скачать PNG DiceBear для существующих аватаров и обложек мероприятий, затем заменить их в PostgreSQL. Запускать после `make seed_db`: повторное наполнение возвращает исходные изображения. Требуются доступ к интернету и работающая БД; API-ключ не нужен. |

| `make index_research` | Через `python3` выполнить по 500 замеров с индексом/без него на 1000, 2000, 5000 и 10000 событий; построить график matplotlib. |
| `make test` | Существующие unit-тесты `./internal/service`, без БД. |
| `make allure-test` | Девять unit-сценариев ЛР1 для отзывов: классические, лондонские и PostgreSQL-репозиторий; без БД, результаты в `allure-results`. |
| `make allure-serve`, `make test-report-serve` | Запустить тесты ЛР1 и веб-отчёт с Allure и покрытием на localhost:9001; Go, Python, npm и Java. Allure CLI автоматически устанавливается в `.test-tools`. |
| `make test-report` | Запустить сценарии ЛР1 и сохранить HTML Allure и покрытия в `test-report`, без веб-сервера. |
| `make integration_test` | Существующие HTTP/PostgreSQL-тесты через testcontainers, нужен Docker. |

Наполнение использует Faker (`ru_RU`, seed=42), `scripts/seed_data.json` и Pillow для PNG. В прикладных таблицах более 1000 строк, кроме справочника из 99 категорий и журнала триггера примерно на 500 строк. Удаляются 5% событий. Учебный вход: `user_1` (admin), `user_2` (user), пароль `password`.

`scripts/dicebear_images.py` заменяет имеющиеся изображения через стили `lorelei` и `landscape`. Скачивает до 100 PNG с паузой 0,1 с между запросами, затем сохраняет пачку одной транзакцией и печатает прогресс в терминал. После остановки или сбоя повторный запуск пропускает уже замененные изображения. Обложки отделяются от аватаров, поскольку после `make seed_db` они ссылаются на одни и те же строки `image`. Скрипт не запускается автоматически.

Исследование создаёт временные таблицы и не меняет рабочие данные/индекс. Результаты прямо в `scripts`: `index_samples.csv`, `index_results.json`, `index_chart.svg`. Методика описана в `../PLAN.md`. Не возвращать папку `research` и старые одиночные замеры. Обычный запуск через `python3`, без временного venv и дополнительных переменных окружения. В Ubuntu при запрете PEP 668 установка: `pip install --user --break-system-packages -r scripts/requirements.txt`.

Swagger UI — `/swagger/index.html`. Пакет `JoinUp/docs` импортируется контроллером, но генерируется и исключён из Git: без `make swagger` свежая копия не соберёт сервер/интеграционные тесты. Makefile использует `@latest` для генераторов Swagger и новых миграций. `make install` выполняет также `go mod tidy`, поэтому может менять зависимости.

В `.PHONY` объявлены `build`, `run_local`, `stop_local`, `mongo_seed`, но рецептов у них нет. Не используй их как рабочие команды сборки/запуска. `PROD` передаётся Makefile, но режим логгера читается из YAML.

Статическая раздача в `internal/controller/server.go` смотрит на `frontend/index.html` и `frontend` относительно рабочей директории. При запуске из `app` это не соседняя `../frontend`; не рассчитывай, что backend автоматически обслуживает существующий SPA. CORS middleware в сервере не настроен.

## Проверки и навигация при изменениях

Unit-тесты находятся в `internal/service/event_test.go` и `user_test.go`, используют testify и ручные моки из `event_test.go`. Allure-сценарии отзывов и описание запуска — в `TESTING.md`; фикстуры управляются BeforeAll/BeforeEach/AfterEach/AfterAll. Классические и репозиторные сценарии используют настоящее PostgreSQL API репозитория/UOW над `internal/testutil/review_connection.go` с хранилищем и транзакциями в памяти. `Pool`/`NewReviewRepo` принимают `sqlRun`, `NewUOW` — интерфейс BeginTx; сервер передаёт обычный pgxpool. Хелперы testutil доступны только с build tag `allure`. Интеграционные тесты в `internal/integration_test/server_test.go` поднимают `postgres:16-alpine`, применяют встроенные миграции и вызывают Echo через httptest. `go test ./...` включает их, поэтому требует Docker и сгенерированный Swagger.

В интеграционном сценарии обновления осталась фиксированная дата июля 2026 года, тогда как сервис запрещает события в прошлом. В сценариях создания используется время через сутки после запуска. Для курсового отчета добавлены три проверки ограничений в `internal/integration_test/constraints_test.go`; выборочный запуск вместе с успешным созданием описан в `TESTING.md`. При разборе падений сначала сопоставь даты с текущим временем; не приписывай такие ошибки новой правке автоматически. Наличие команд в этой памятке не означает, что проверки уже выполнены или проходят.

Для изменения API проследи цепочку: маршрут → DTO/валидация → handler и его интерфейс → service → контракт репозитория → обе реализации → схема/преобразования. Учитывай потребителей в `cmd/cli/main.go` и `../frontend/src/api`, `../frontend/src/types.ts`. Актуальные маршруты и DTO важнее старых TODO и Swagger-аннотаций: например, TODO в `cmd/server/main.go` ещё предлагает DTO и PUT с ID, хотя они уже существуют.
