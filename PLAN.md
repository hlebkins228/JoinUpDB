## 2. PostgreSQL-триггер для журнала удаления мероприятий

**Цель:** записывать факт мягкого удаления мероприятия в отдельную таблицу средствами PostgreSQL.

Сейчас удаление события реализовано как `UPDATE event SET deleted = true`, поэтому нужен триггер на обновление, а не на SQL-операцию `DELETE`.

### Поведение

- Создать таблицу `event_deletion_log` с полями `id` (идентификатор записи), `event_id` (ID мероприятия), `deleted_at` (время удаления в UTC).
- Создать одну триггерную функцию и один триггер `AFTER UPDATE OF deleted ON event FOR EACH ROW`.
- Выполнять запись только при переходе `OLD.deleted = false` → `NEW.deleted = true`.
- Изменение названия, описания и других полей, а также повторная установка `deleted = true` не должны создавать запись в журнале.
- Запись журнала выполняется в той же транзакции, что и удаление: при откате изменения события запись журнала тоже откатывается.

### Места изменений

- Новая Goose-миграция в `app/migrations/`: создание таблицы, функции и триггера в `Up`; удаление триггера, функции и таблицы в `Down`.
- Существующий `DeleteEvent` в `app/internal/repository/postgres/event.go` уже обновляет флаг `deleted` и будет запускать триггер без отдельной записи журнала из Go.

Задача относится только к PostgreSQL. Для учебной демонстрации журнал просматривается SQL-запросом; отдельный API или интерфейс для него не требуется. Сохраняются только ID события и время удаления.

### Проверка результата

Вручную удалить мероприятие через существующий API и проверить запись в `event_deletion_log`. Проверить отсутствие новых записей при обычном редактировании и повторной установке флага. В отдельной SQL-транзакции установить флаг удаления и выполнить `ROLLBACK`: ни удаление, ни запись журнала не должны сохраниться.

## 3. Правдоподобное наполнение PostgreSQL

**Требования:** более 1000 строк в каждой прикладной таблице. По уточнению пользователя для журнала триггера допустимо около 500 записей. В служебные таблицы фиктивные данные не добавлять.

**Реализация:** `app/scripts/seed.py` использует Faker с русской локалью и фиксированным seed; темы встреч, описания, города и тексты отзывов хранятся в одном `seed_data.json`. Изображения — корректные PNG, созданные Pillow.

- 5001 пользователь, у каждого 1–3 своих мероприятия.
- Каждый пользователь участвует в 4–9 чужих мероприятиях в своём городе и подписан на 2–5 других пользователей.
- Отзывы пишут участники только прошедших встреч; даты регистрации, создания встречи и отзыва согласованы.
- В справочнике 1111 категорий: 11 основных направлений и учебные сочетания тем и форматов. У события основная категория и уточняющая тема.
- 5% мероприятий мягко удаляются, журнал заполняется самим триггером. Удалённые события обратно не восстанавливаются.
- Неиспользуемые `preset` и `subscribe` остаются в схеме и заполняются, новый API для них не добавляется.

Команда: `make seed_db`. Она заменяет учебные данные в текущей БД. Вход: `user_1` — администратор, `user_2` — пользователь; общий учебный пароль `password`.

## 4. Роли PostgreSQL: гость, пользователь и администратор

Роли создаются обычной Goose-миграцией `20260924002000_roles.sql` при `make migrate_up`. Отдельная команда настройки не нужна. Пароли новых учебных ролей: `guest`, `user`, `admin`; пароли существующих ролей миграция не меняет.

- `joinup_guest` читает общедоступные таблицы; права проверяются отдельным подключением.
- `joinup_user` используется backend для чтения и изменения прикладных данных.
- `joinup_admin` запускает наполнение и имеет полный набор привилегий на прикладные таблицы и последовательности.
- Миграции выполняются владельцем БД `postgres`.

`make check_roles` сохраняет проверки подключений в `app/scripts/permissions.csv`. При откате миграции отзываются выданные права текущей БД; роли сохраняются, поскольку они общие для всего кластера PostgreSQL.

## 8. Исследование влияния индекса

`make index_research` запускает `app/scripts/index_research.py` через обычный `python3`. Зависимости всех Python-сценариев перечислены в `app/scripts/requirements.txt`.

**Методика:**

- По оси X — 1000, 2000, 5000 и 10000 мероприятий. Набор фильтров фиксирован: Москва и диапазон дат ±30 дней от начала генерации. Сравнивается индекс `(city, event_date, id) where deleted = false` и его отсутствие.
- Количество записей выбрано как управляемый фактор роста. Количество фильтров само по себе не задаёт трудоёмкость: важны их тип и доля подходящих строк. Утверждение, что один фактор всегда сильнее другого, не делается.
- Используется основной SQL из `EventRepo.SearchEvents`. Догрузка связей, сеть, HTTP и отрисовка интерфейса в измерение не входят.
- Набор создаётся во временных таблицах; размеры являются вложенными подмножествами одних данных. Число локаций, параметры фильтров и настройки соединения постоянны. Рабочая БД и её индекс не изменяются.
- Для каждой точки и каждого варианта — 10 блоков по 50 замеров, всего 500. Перед каждым блоком варианта — 10 прогревочных запросов. Порядок вариантов чередуется, сборка индекса и генерация данных во время запроса не включаются.
- Измеряется серверный `Execution Time` через `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)`. Планирование сохраняется отдельно. Кеш прогрет; выбросы не удаляются.
- График matplotlib показывает арифметическое среднее и оценку 95% доверительного интервала по средним 10 блоков. Измерения в блоках могут быть коррелированы; результат относится к данному окружению и временным таблицам с local buffers.

Все результаты лежат прямо в `app/scripts`: `index_samples.csv` — 4000 исходных замеров; `index_results.json` — средние, разброс, планы и описание условий; `index_chart.svg` — единственный график. Отдельная папка `research` удалена.

**Последний проверенный запуск:**

| Мероприятий | Без индекса, мс | С индексом, мс |
| --- | --- | --- |
| 1000 | 0.3422 | 0.2169 |
| 2000 | 2.0937 | 1.7484 |
| 5000 | 2.9162 | 2.0680 |
| 10000 | 4.6985 | 2.9085 |

При переходе от 1000 к 2000 мероприятий PostgreSQL сменил Nested Loop на Hash Join; этим объясняется скачок времени обеих серий. Индекс использован во всех четырёх вариантах с индексом. Измеренное ускорение относится к этому набору данных и выбранным фильтрам.
